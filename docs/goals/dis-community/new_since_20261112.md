## I251.c8 · 新增 · Ashley-QwQ · 2026-11-12T07:03:56Z

[Getting empty burned disc when calibrating boundary with CD-R](https://github.com/JiaFeiMiao-K-Cat/DiscImageStudio/issues/251#issuecomment-6817119300)

@YukaiP Sorry for the slow reply, and thanks for trying disc-probe and posting the output.

Your screenshot shows a bug on our side. For CDs, disc-probe only ever suggests 1411 or 2822, so it kept sending you back to speeds you had already tried. At those speeds your drive keeps a constant linear speed (CLV), and in that mode disc-probe can't work out where each sector sits on the disc.

Many drives only switch to a constant spin (CAV) at their higher CD speeds. Could you try these in order, and stop at the first one that says CAV?

```
python -m discprobe timing --drive E: --media cd --speed 4234
python -m discprobe timing --drive E: --media cd --speed 5645
python -m discprobe timing --drive E: --media cd --speed 7056
```

If all three still say CLV, your SH-216DB probably never spins a CD at a constant rate, and disc-probe can't measure CD geometry with it yet. I'm fixing the speed suggestions so they stop repeating, and looking into whether a CLV drive can still be used. I'll post an update here.

## The pattern *is* written — it is rotated. Geometry sweep results

Following the earlier comments, I found a way to separate "no contrast" from "wrong geometry": the half-black/half-white image does show structure if you look closely — but the dividing line arrives as a **spiral**, not as a straight diameter. So the two-level pattern is being recorded; it is rotated by an angular error that accumulates with radius.

That makes the drift measurable: the distance between consecutive turns of that spiral is the drift per revolution.

### Method

Same image (`angular.png`, left half pure white / right half pure black), same command, same drive (`GH22NS30`), same media, `--tone-dither 0`, burned at 16×. Only `--outer-radius-mm` changes, always with `--total-sectors 2297888` (the disc's own `Track Size`) and `--fill-sectors 2297824`.

Ring count is measured over the **first 10 mm** from the inner data edge, with a steel rule laid on the disc.

| `--outer-radius-mm` | rings per 10 mm | implied spacing |
| --- | --- | --- |
| 58.040 | 18 | 0.56 mm |
| 58.008 | 16 | 0.63 mm |
| **57.800** | **6** | **1.67 mm** |

Photos of the first two measurements (rule in frame, same disc surface):

![r1 = 58.040 — 18 rings per 10 mm](https://raw.githubusercontent.com/ghpo/discimagestudio-evidence/main/midia-1medicao.jpg)

![r1 = 58.008 — 16 rings per 10 mm](https://raw.githubusercontent.com/ghpo/discimagestudio-evidence/main/midia-2medicao.jpg)

### The part that does not fit

At `r1 = 57.800` the first centimetre improves a lot (18 → 6 rings), **but the spacing keeps shrinking with radius**: after that first centimetre the rings become progressively finer until there are more than 70 of them and a phone camera can no longer resolve them.

For a constant pitch error the spacing would be **constant** across the radius. For a linear pitch coefficient (`--pitch-linear a1`) it would vary smoothly. Fitting the observed 5–10× change in spacing to `pitch(r) = p0 (1 + a1 x)` requires `a1 ≈ -5`, i.e. a negative track pitch — physically impossible.

So the residual is **not** a radius or pitch error that the documented parameters can express. What remains is the mapping between sector number and physical angle: the model assumes the ideal CLV relationship, and this drive appears to deviate from it in a way that varies with radius.

### Questions

1. Is there any CLI parameter (or a value the GUI's fine calibration produces) that compensates for a sector→angle mapping deviation rather than a radius/pitch deviation?
2. Does the GUI's spoke calibration measure exactly this — and would its result be usable from the CLI via `--pitch-*`? If so, which coefficient carries the angular term?
3. If this is a known drive limitation, is there a list of drives known to work? Both drives here are HLDS (`GH22NS40`, `GH22NS30`), consistent with the pattern noted earlier.

For completeness: with the unmodified preset geometry (`--total-sectors 2296437`, `r1 = 58.04`) the same image produced a disc that looked completely uniform, and the drift only became visible as a measurable spiral after switching to the disc's real sector count. That step alone may be worth documenting.

Happy to run more experiments — both drives and sacrificial media are still available. A flatbed scan of the disc is also possible if that would help quantify the spacing profile.

## 为什么

默认流程漏掉了空盘 `info` 这一步，但标定和 `disexport --sectors` 都需要空盘报告的可用扇区数。原来 `guide` 和引导控制台从 `list` 直接走到随机数据盘。

## 改了什么

- 在 `list` 之后、随机数据盘之前加入 **Blank disc (info)** 步骤；`guide`、清单、编号回退和 TUI 控制台同时生效。
- 步骤上显示读到的数量（如 `2,295,104 sectors available`），并带进下一条随机盘提示。
- 只有**同盘型的空盘**报告才会打勾：刻过的盘读回来的数可能偏大；`incomplete`（写了一半、未封盘）不算空盘；CD 的 ATIP 导出口、以及没有 track 空闲块的空 BD 容量仍算空盘容量。
- 已经做过随机盘或 `timing` 的用户不会被拉回这一步：清单里它保持未做，但不挡后面的步骤，也不标“现在到这里”，下一条命令直接做图片 ISO。
- `info` 结果按 CD/DVD/BD 盘型筛选，不会拿另一种盘的报告打勾。
- 教程改为 6 步；README 中英文和两份手册同步更新。
- 非交互脚本现在看到 6 个默认步骤（多出空盘检查这一行），这是有意的。

## 验证

- `python -m discprobe selftest` -> `all checks passed`
- 新增测试覆盖：DVD 报告不勾 BD 步骤、`incomplete` 盘不算空盘、已做 timing/geo 的用户不回到 info、空 BD 容量回退。
- `python -m discprobe guide` 第一条命令现在是 `python -m discprobe info --drive ...`。
- `python -m discprobe menu` 从新的空盘步骤开始。

基于 #32 合并后的最新 `main`。
